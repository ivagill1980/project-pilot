Project Pilot

把超大型软件项目变成一个始终可定位、可验证、可恢复的闭环控制系统。它不会只告诉你“下一步做什么”，而是让你在做每一步时始终知道：最终目标是什么、现在在整个计划的哪里、完成了多少、为什么现在做这件事。

核心原则：One Thing in Context.
核心模型自适应推进每轮导航 HUD三种模式Rescue命令状态文件对话演示使用方式

1. 它不是 TODO 工具，而是项目控制层

Project Pilot 持续比较“目标状态”和“项目现实”，然后决定下一步。计划不是事实；代码、测试、CI、运行结果和最新决策共同构成现实。运行证据说明当前行为，但仍要单独检查它是否满足目标。

01

保持方向

最终目标、Phase、Milestone、Task、Step 始终形成完整坐标。

02

控制漂移

发现计划、文档、架构、范围、验证体系与实际代码的偏离。

03

随时恢复

中断后不是读完整聊天历史，而是从项目状态和 checkpoint 重建“YOU ARE HERE”。

04

按风险选路

根据不确定性、反馈成本、可逆性和耦合度，选择交付、探索或恢复动作。

05

先命名病因

症状先归因再开方：固有障碍要改机制，用法错误要改设置。不是所有问题都值得"再 prompt 一次"。

2. 自适应推进：先判断现在缺什么

当前节点先标记工作类型，再决定最小动作。探索可以否定一条路线，但不能被计入产品完成度。

DELIVERY 交付

目标和成功信号比较清楚，做一个可回退、可观察的小切片。

EXPLORATION 探索

关键假设尚未证实，先用原型、基准、fixture 或模拟缩小方案空间。

RECOVERY 恢复

基线、验证信号或项目控制面不可信，先恢复它们再继续产品路径。

四个判断

不确定性高而反馈便宜时先实验；耦合或回退成本高时先定义边界、影响和恢复路径；没有可信成功信号时先建立验收样例。

卡住时的两条出路

Playground：卡住或面对不熟的库时停止自上而下调试，在一个版本控制忽略的临时目录里把假设直接试出来，再照着结论实现。

多方案共用一道门：路线本身未定时，造几个小变体、给它们同一道验收门，比较后显式选定并记录。翻版算探索进度，不算交付。

处置阈值：改代码前先提交；同一路线第 2–3 次仍不改善就回退重来（显式要求 git reset --hard），而不是继续在失败方案上打磨。

HUD 有两种档位

全量头：阶段或里程碑切换、中断后恢复、会话第一轮、以及你要求"看全局"时使用。

紧凑头：同一任务的连续微步压到三行——目标与进度、坐标与工作类型、NOW 与 DONE WHEN。字段一个不少，只是不再分行。

细节进正文，不进头部。随时用 看全局 / 看当前 切档。

标记只有在"可能不出现"时才有信息量

🧪 必须与当前实际选择的工作类型一致。

♻️ 表示这一轮确实重读过持久状态（中断恢复后，或意识到上下文已衰减时）。

条件不成立就不写该标记；该出现而没出现才是信号——说明上下文已经衰减，此时重读状态、重申标记、再继续。

4. NORMAL / RECONCILE / RESCUE

Skill 不要求从项目第一天开始使用。任何已有项目都可以接入；状态越混乱，越倾向从 Rescue 开始。

NORMAL正常推进地图可信、验证健康，继续小步交付。
RECONCILE轻度偏航计划与现实出现差异，校准而不推翻基线。
RESCUE严重失控先考古、重建现实，再重新基线和稳定。

5. Rescue：随时加入一个已经混乱的项目

Rescue 的第一原则：刚进入项目时不要冲动重构。先只读调查，把“文档声称什么”和“代码/测试证明什么”分开。

Evidence Hierarchy

↑ 高可信
├─ 运行/生产事实（当前行为）
├─ Tests / CI / schema / migrations
├─ 当前代码和配置
├─ 最近合并的工作
├─ 已接受 ADR / Specs
├─ 当前文档
├─ 旧 Roadmap / TODO
└─ 推测
↓ 低可信

这是判断“现在怎样”的顺序；是否满足需求还要单独核对。

Drift Detector

Plan 计划与实际路径分离

Docs 文档描述已不存在的系统

Architecture 边界被逐步穿透

Scope MVP 不断膨胀

TODO 旧 TODO / FIXME 与现状矛盾，或掩盖着活的依赖

False Completion UI/API/schema 看似都有，但关键链路没闭环

Validation 测试或 CI 已不代表真实成功，却仍红着继续加功能

Decision 已定的选择被反复重开，却没有新决策

Assumption 计划依赖已被推翻、或从未被写明的假设

Evaluation 成功信号本身不可信（覆盖率高，但断言空洞）

History Mining

考古时顺带挖一遍版本历史：

热点 = 变更频率 × 复杂度。风险集中，而且会被反复读进上下文。

变更耦合 = 总是一起改、却看不出依赖关系的文件——通常说明边界画错了位置。

指标只负责提名，判断来自读代码。幸存者作为重构目标进计划，而不是当成代码的事实。

关键设计：进入支线任务时永远记录 ↩ RETURN TO。支线可以很深，但主线坐标不会丢失。

7. Skill 用什么保持“项目记忆”

聊天不是唯一事实源。Project Pilot 把导航状态持久化，让新 session 可以从文件恢复，而不是依赖模型记住之前全部对话。

推荐控制目录

.project-pilot/ ├── STATE.md # 当前坐标和下一动作 ├── MAP.md # 全项目层级与进度 ├── HEALTH.md # CI / 测试 / 漂移 / 风险 ├── RECOVERY.md # Rescue 过程与返回目标 ├── PARKING_LOT.md # 支线想法 ├── DECISIONS.md # 关键决策索引 ├── SESSION_LOG.md ├── plans/ │ ├── active/ │ ├── completed/ │ └── abandoned/ └── snapshots/

状态不是文档堆

AGENTS.md：稳定规则与地图入口，不放大量临时状态。

Reference docs：架构、产品、约定等长期知识。

Checkpoint / STATE：当前 session 可恢复状态。

Tests / hooks / scripts：把可确定的验收从语言模型转移给机器执行。

文件地图：常驻核心 + 按需读取

SKILL.md 只放每一轮都要用的东西（不变量、交互契约、命令、安全、质量清单）；其余按需读取：

├─ references/build-mode · reconcile-mode · rescue-mode
├─ references/state-schema · evidence-record · decision-policy
├─ references/knowledge-maintenance · diagnosis · team · multi-agent
├─ references/output-patterns · pattern-router
├─ templates/ 七个状态文件模板
└─ scripts/project_state.py 状态工具

原因很直接：常驻内容越长，越容易被截断和稀释。所以新增内容优先放进 references/，主入口只留触发条件。

格式靠机制，不靠自觉

python scripts/project_state.py init .project-pilot # 从 templates/ 生成七个状态文件 python scripts/project_state.py validate .project-pilot # 校验字段、枚举、节点 id、依赖与证据 python scripts/project_state.py progress .project-pilot # 沿 parent 链把进度汇聚上去 python scripts/project_state.py drift . # 扫描仓库：文档死链与过期 TODO python scripts/project_state.py selftest # 用已知好/坏样例自检工具本身

机检项：必填字段与枚举、日期与进度范围、节点 id 唯一、depends_on 与 parent 目标存在且无环、证据记录必须带 recheck_when。

进度不再是估计值：progress 沿 parent 链建树，容器取子节点加权平均（权重规则由 progress_policy 决定），unknown 子节点不计入均值，容器自称的进度与汇聚不符会告警——子节点才是事实来源。

最关键的一条：没有证据 id 的 VERIFIED 节点直接报错——进度声明不能凭感觉填。退出码 0 干净、1 有错，--strict 把警告也算错。仅标准库，Python 3.8+。

9. 如何使用

`SKILL.md` 是完整工作流定义。把它安装为 Codex/兼容 Agent Skills 的 Skill 后，在目标仓库中通过自然语言调用即可。大型已有项目建议第一次直接说“接管这个项目并校准真实状态”。

安装 Skill

使用本页配套的 SKILL.md。Skill 格式遵循 Agent Skills / OpenAI Skills 的 Markdown 工作流模式。

第一次进入仓库

Skill 会先判断 BUILD、RECONCILE 还是 RESCUE；已有复杂项目通常先做轻量 archaeology。

建立项目地图

Project → Phase → Milestone → Task → Step。全局地图稳定，当前附近才做细规划。

生成并校验控制状态

用 scripts/project_state.py init 从模板生成，用 validate 机检。没有证据的 VERIFIED 会被判错，而不是被相信。

进入闭环

Select → Act → Verify → Record → Navigate。每次小步都有机器可观察的完成门。

发现失控

先 Reconcile；严重时自动建议 Rescue → Rebaseline，而不是继续在错误计划上堆 patch。

最简单的首次指令：
接管这个项目。先不要改代码，重建真实项目地图，告诉我整体完成情况、当前位置、主要漂移和最合理的下一步。
